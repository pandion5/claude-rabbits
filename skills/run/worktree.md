# 워크트리 격리 규약

SKILL.md 단계 3(파견)·단계 4(검토)에서 격리가 발동했을 때만 읽는다.

## 단계 3 — 격리 파견

- **워크트리 격리**: 파일을 변경하는 워커 **2명 이상을 병렬** 파견하거나(충돌 위험), 실험적·
  위험한 변경을 워커 1명에게 맡길 때 — 하니스 Agent 툴이 워크트리 격리(`isolation: 'worktree'`)를
  지원하면 각 워커를 그 옵션으로 파견해 충돌을 원천 차단한다. **세션에 워크트리 관리를
  제공하는 환경 스킬/CLI가 로드돼 있으면 그 방식을 우선한다** — 커맨드는 버전마다 달라 그
  스킬의 버전 매칭 가이드를 조회해 사용하고(추측 호출 금지), 제공되지 않거나 리졸브 실패 시
  위 `isolation: 'worktree'` 방식으로 폴백한다. 추적 원장(예:
  `.rabbits/qa-checklist.md`·`.rabbits/backlog.md`) 갱신 작업은 격리 금지 — 원장 반영은 대장 몫, 워커에게 시키지
  않는다. 격리 워커의 `{{제약}}`에 반드시 주입: "cwd=전용 워크트리, 팩 경로는 상대 해석,
  워크트리 밖 쓰기 금지" + "작업 완료 시 워크트리에서 반드시 커밋"(미커밋이면 정리 단계에서
  산출물이 통째로 삭제될 수 있다). 단일 변경 워커·읽기전용 워커는 격리 불필요(셋업 비용 회피).
  격리 옵션이 거부되면 무격리로 재파견하고, 파일 변경 워커는 순차 파견한다.

## 단계 4 — 회수·정리

- **격리 워커 회수·정리(검토 전)**: 격리 파견한 워커가 반환하면 검토보다 먼저 반환 메타의
  `worktreePath`·`worktreeBranch`로 위치를 파악해 회수한다(파일 복사 또는 브랜치 병합). 정리 전
  `git -C <worktreePath> status --porcelain`이 빈 값인지 확인 — 비어있지 않으면(미커밋 잔존)
  파일을 먼저 회수한 뒤에만 `git worktree remove --force` + 브랜치 삭제로 정리한다(변경 없는
  워크트리는 하니스가 자동 정리).
