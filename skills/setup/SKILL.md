# rabbits setup — 프로젝트 플러그인 셋업

너는 이 셋업의 **진행자**다. 대상 리포의 스택을 근거와 함께 제시하고, 사용자가 고른 프로필의
플러그인만 프로젝트 범위에서 추가로 켠다.

플러그인과 스킬이 많이 설치된 환경에서는 세션에 주입되는 스킬 목록이 크기 한도에 걸려 뒤쪽 스킬의
설명이 잘리고, 설명이 비면 모델이 그 스킬을 고르지 못한다. 프로젝트마다 필요한 플러그인만 켜두면
목록이 짧아지는데, 이 스킬은 그중 프로젝트 쪽만 맡고 전역 설정은 사용자가 직접 정리한다.

**시작 선언:** "rabbits 셋업 시작 — 대상 <리포 경로>, 스코프 <project 또는 local>"

## 하드제약 (위반 시 즉시 중단)

1. **자동 적용 금지**: 사용자가 이 스킬을 명시적으로 호출했을 때만 동작한다. 다른 스킬이나 런의
   곁가지로 실행하지 않는다. 단계 3의 선택을 받기 전에는 어떤 플러그인도 켜지 않는다.
2. **기존 설정을 끄지 않는다**: 하는 일은 추가 활성화뿐이다. `claude plugin disable`을 쓰지 않고,
   settings 파일을 직접 편집하지도 않는다. 변경은 `claude plugin enable`로만 한다.
3. **설치와 활성화는 별개로 보고**: 설치되지 않은 플러그인은 건너뛰고, 보고에 `claude plugin
   install <id>` 명령만 적어 안내한다. 대신 설치하지 않는다.
4. **적용 시점 명시**: 플러그인은 세션 시작 시 로드되므로 지금 세션에는 반영되지 않는다. 보고에
   "다음 세션부터 적용됨"을 반드시 적는다.
5. **상태 파일 금지**: `.rabbits/setup.json` 같은 별도 상태 파일을 만들지 않는다. 결과는 CLI가
   기록하는 settings 파일에만 남는다.
6. **CLAUDE.md는 옵션**: 인자에 `--with-guide`가 있을 때만 스킬 안내 절을 쓴다. 기본은 쓰지 않는다.
7. **매핑 밖 활성화 금지**: 단계 2의 프로필 매핑에 없는 플러그인은 켜지 않는다. 웹 프로젝트라고
   모바일을 같이 켜지 않고, 문서가 있다고 `gs-cert`를 켜지 않는다.
8. **전역 설정 변경 금지**: `~/.claude/settings.json`은 건드리지 않는다. 스코프는 project 또는
   local만 쓴다.

## 단계 0 — 인자와 현황 확인

인자: $ARGUMENTS (`--scope project|local`, `--with-guide` 모두 선택. 스코프 기본값은 `project`)

- `claude plugin list --json`으로 설치 목록과 유효 활성 상태, notes를 한 번에 읽는다. 여기서
  나오는 `enabled` 값이 전역·프로젝트·로컬을 합산한 유효 상태다. 이미 켜진 판정은 이 값으로 한다.
- 대상 리포의 `.claude/settings.json`과 `.claude/settings.local.json`에 `enabledPlugins`가 있는지
  확인해 현재 프로젝트 범위 설정을 파악한다.

## 단계 1 — 스택 감지

아래 신호를 찾아 **근거를 파일 경로와 함께 나열**한다. 신호 하나로 스택을 단정하지 않는다.

- 웹: `package.json`의 의존성에 `react`, `next`, `vite` 등이 있는지.
- 모바일: `package.json`의 `react-native`·`expo`, 또는 `pubspec.yaml`, 또는 `android/`·`ios/` 폴더.
- 문서: `docs/` 아래 문서, 산출물 문서(보고서·매뉴얼·제안서), `.hwp`·`.docx`·`.pptx`·`.xlsx` 파일.

근거가 약하면 약하다고 적는다. 감지 결과는 추천의 재료일 뿐이고, 결정은 단계 3에서 사용자가 한다.

## 단계 2 — 프로필 추천

프로필은 네 가지이고 복수 선택이 가능하다.

| 프로필 | 켜는 플러그인 |
|--------|--------------|
| 웹 | `frontend-design@claude-plugins-official`, 디자인 비중이 크면 디자인 플러그인 하나 추가 |
| 모바일 | `frontend-mobile-development@claude-code-workflows` |
| 문서 | `paperworker@paperworker`, GS 인증 업무가 있으면 `gs-cert@gs-cert-local` 추가 |
| 없음 | 추가로 켜는 것이 없다 |

"없음"은 다른 프로필과 함께 고를 수 없고, 기존 설정을 끈다는 뜻이 아니라 이번에 추가 활성화를
하지 않는다는 뜻이다. 선택 화면에서 이 점을 한 줄로 밝힌다.

디자인 플러그인은 둘 중 하나를 사용자가 고른다. 차이를 한 줄로 설명한다.

- `impeccable@impeccable`: 화면 하나를 방향 잡기부터 마감 검토까지 끌고 가는 쪽.
- `ui-ux-pro-max@ui-ux-pro-max-skill`: 브랜드·디자인 시스템·배너·슬라이드까지 폭이 넓은 쪽.

`gs-cert@gs-cert-local`은 GS 인증 업무가 실제로 있다고 사용자가 확인한 경우에만 후보에 넣는다.

## 단계 3 — 선택 받기

AskUserQuestion으로 두 가지를 묻는다. 감지 근거를 질문에 함께 보여준다.

1. 프로필(복수 선택 가능, "없음"은 단독 선택). 웹을 고르면 디자인 플러그인 여부와 종류,
   문서를 고르면 GS 인증 업무 여부를 이어서 묻는다.
2. 스코프. `project`는 `<리포>/.claude/settings.json`에 기록돼 커밋 대상이 되고, `local`은
   `<리포>/.claude/settings.local.json`에 기록돼 gitignore 대상이다. 기본값은 `project`이며
   인자로 스코프가 이미 주어졌으면 다시 묻지 않는다.

"없음"을 골랐거나 켤 대상이 남지 않으면 단계 4를 건너뛰고 단계 5에서 그대로 보고한다.

## 단계 4 — 활성화

선택된 플러그인을 하나씩 처리한다.

- 단계 0에서 확인한 유효 활성 상태가 이미 켜짐이면 실행하지 않고 건너뛴 것으로 분류한다.
- 미설치면 실행하지 않고 미설치로 분류한다.
- 나머지는 `claude plugin enable <id> --scope <스코프> --json`을 실행하고, 종료 코드와 출력으로
  성공과 실패를 가른다.

## 단계 5 — 보고

아래 네 가지를 나눠서 적는다.

1. 켠 플러그인: id와 적용된 스코프, 기록된 settings 파일 경로.
2. 건너뛴 플러그인: 이미 켜져 있던 것.
3. 미설치라 건너뛴 플러그인: id와 `claude plugin install <id>` 명령.
4. 실패한 플러그인: id와 오류 한 줄.

하나라도 켰으면 "다음 세션부터 적용됨"을 적고, 켠 것이 없으면 "변경 없음"이라고 적는다.
프로젝트 스코프로 켰으면 `.claude/settings.json`이 커밋 대상이라는 점도 한 줄 덧붙인다.

## 단계 6 — 스킬 안내 절 (`--with-guide`일 때만)

- 대상 리포의 `CLAUDE.md`를 읽어 `## 스킬 사용 안내` 절이 이미 있으면 아무것도 하지 않고
  "이미 있어 건너뜀"이라고 보고한다.
- 없으면 파일 말미에 그 절을 추가하고, 이번에 켠 플러그인의 스킬을 언제 쓰면 되는지 한 줄씩 적는다.
- `CLAUDE.md`가 없으면 만들지 않고 건너뛴 것으로 보고한다.
